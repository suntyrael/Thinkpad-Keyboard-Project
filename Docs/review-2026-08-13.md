## 结论摘要

分支核心改动（BMD-340 引脚重映射 + `GPIO_DS_ALT_*` 移除 + CHG_INT 迁移）经与官方数据手册和网表交叉核对**正确且自洽**。但存在 **8 个确定性代码缺陷**（其中 3 个影响用户可见行为：采样率校验越界读、按键 sync 标志错误、滚轮负向解码错误）、**1 个硬件配置疑点**（矩阵列驱动方式与项目已验证修复矛盾）、**1 个功能未接线问题**（TrackPoint 参数调节行为因缺少 devicetree 节点完全未编译）及若干电源管理、构建可复现性、文档同步问题。

## 一、P1 高优先级

### 1.1 矩阵列驱动方式与 v1.0.29 已验证修复矛盾（硬件回归风险）【需实机验证】

- **位置**：`module/boards/thinkpad/thinkpad_wireless/thinkpad_wireless.dts`（`matrix_kscan` 节点，col-gpios 全部为 `GPIO_ACTIVE_LOW`，无 `GPIO_OPEN_DRAIN`）
- **问题**：开发日志 v1.0.29 明确记载：列驱动推挽（push-pull）时，未扫描的 15 列输出 3.3V 高电平，高电平电流经二极管倒灌至 SENSE 线，导致"左侧大部分按键无响应"；改为 `GPIO_OPEN_DRAIN` 后**实机验证通过**。但提交 `41c365b`（revert，2026-08-04）在 42 分钟后将 open-drain 改回推挽，并同时移除了 `CONFIG_ZMK_KSCAN_MATRIX_POLLING`（回到中断驱动）。当前分支即此状态，**开发日志没有任何条目解释为何撤销已验证的修复**。
- **影响**：当前矩阵驱动方式 = 日志中记载的"故障态"。若 BMD-340 v2 板尚未实测，此状态可能未经验证；同列多键或跨列同按场景存在回退风险。
- **建议**：
  1. 实机验证矩阵扫描（尤其左侧键区与同列 ≥2 键同按 + 休眠唤醒）；
  2. 若正常，在开发日志补充实测记录；若异常，恢复 `GPIO_OPEN_DRAIN` 或给出推挽 + 中断驱动的实测依据。

- **电气分析（2026-08-13 讨论补充）**：
  - OD + 无上拉时，未扫描 DRV 列确实浮空、电平不确定（观察正确），但**不影响扫描结果**：row 读取只依赖"扫描列强拉低"与"row 自身 13k 内部上拉"两个因素；浮空列高阻，既无能力拉低 row（无驱动能力），也不会阻止扫描列拉低 row（不并联分流）。二极管结构保证浮空列无论被耦合到 ~0V（反偏截止）还是 ~3.3V（无压差无电流）都不影响 row 电平。
  - 推挽与 OD 的真正区别：推挽未扫描列**主动输出 3.3V**（倒灌根源，v1.0.29 实测故障）；OD 未扫描列**高阻浮空**（无害）。"确定电平 ≠ 正确电平"。
  - DRV（col）是**输出脚，不需要上拉**；上拉只对 SENSE（row 输入）有意义（已配 `GPIO_PULL_UP`）。因此"OD 依赖上拉才成立"的前提不成立——col 不上拉不影响 OD 方案可行性。
  - 边界场景：中断驱动空闲唤醒时，推挽（col 高）与 OD（col 浮空）面临相同的"row 不产生边沿"问题，非 OD 特有；该场景取决于 ZMK `kscan_gpio_matrix.c` 中断模式对空闲列电平的处置，需查证/实测。

- **决策记录（2026-08-13）**：**保留当前推挽 + 中断驱动设定**，待 PCBA 实机验证后决定。若出现 v1.0.29 记载的倒灌现象（左侧键区无响应 / 同列 ≥2 键异常），再切换为 `GPIO_OPEN_DRAIN`（可同时配 `GPIO_PULL_UP` 消除浮空顾虑，nRF PIN_CNF 支持 OD+弱上拉组合）。

### 1.2 ps2_uart.c 写互斥锁多次释放（并发保护失效）【确定 Bug，潜伏】

- **位置**：`module/drivers/ps2_uart.c`
  - `k_mutex_lock`：L795（`ps2_uart_write_byte`）
  - `k_mutex_unlock`：**3 处** —— L819（`write_byte` 末尾）、L975（`write_byte_start` 内）、L1142（`write_finish` 内）
- **问题**：调用链 `write_byte()` 加锁 → `write_byte_start()` 在 L975 提前解锁 → `write_finish()` 在 L1142（work queue 线程上下文）再次解锁 → `write_byte()` 末尾 L819 第三次解锁。锁的获取/释放路径不平衡：正常路径同一把锁被解锁 3 次。
- **影响**：
  - 第二次及第三次 unlock 发生在非持有者线程（`k_mutex_unlock` 非 ISR/workqueue 安全），Zephyr 调试配置下触发断言，release 下破坏 mutex 计数；
  - 实际传输期间互斥锁处于空闲，第二个线程可并发发起写操作，PS/2 总线上字节可能交错；
  - 若 `ps2_uart_set_mode_write()` 提前失败返回，L975 不执行，则 L819 是唯一解锁——路径相关的不平衡。
- **注意**：当前板使用 `gpio-ps2`（`CONFIG_PS2_UART` 未启用），此缺陷**潜伏未触发**；一旦启用 UART 传输即暴露。
- **建议**：与 `ps2_gpio.c` 对齐——锁/解锁只在 `write_byte()` 内各一次（删除 L975 与 L1142 的 unlock），或改为"加锁在 start、解锁在 finish"的单一配对。

### 1.3 采样率校验 `sizeof` 当元素个数（数组越界读）【确定 Bug】

- **位置**：`module/drivers/input_mouse_ps2.c` L888-889
  ```c
  int rate_idx = zmk_mouse_ps2_array_get_elem_index(
      sampling_rate, allowed_sampling_rates,
      sizeof(allowed_sampling_rates));   // 28 字节，被当作元素个数
  ```
  `allowed_sampling_rates` 为 7 元素 `int[]`（L287-289），`sizeof` = 28；函数按 `for (i=0; i<array_size; i++)` 遍历，实际访问 `allowed_sampling_rates[7..27]`。
- **影响**：越界读（未定义行为）。若越界区域恰好出现目标值，非法采样率（如 30）会被误判为合法并发送给设备；即使不触发误判，越界访问本身即 UB。
- **建议**：改用 `ARRAY_SIZE(allowed_sampling_rates)`（Zephyr `<zephyr/sys/util.h>` 内置）；`zmk_mouse_ps2_array_get_next_elem/prev_elem`（L842-868）若被复用同样注意。

### 1.4 按键上报 sync 标志逻辑错误（静止时右/中键不响应）【确定 Bug】

- **位置**：`module/drivers/input_mouse_ps2.c` L611-657（`zmk_mouse_ps2_activity_click_buttons`）
- **问题**：`buttons_need_reporting` 在 Left 分支后**无条件** `--`，Right 分支后再 `--`。当**只有右键或中键**变化时：
  - 只有右键：运行到 Right 分支时 `buttons_need_reporting` 已递减为 0 → `input_report_key(..., sync=false)`；
  - 只有中键：到 Middle 分支时已为 -1 → `sync=false`。
  `sync=false` 的事件不会立即 flush，需要等下一次 `sync=true` 的事件（移动/左键）才送出。
- **影响**：TrackPoint 静止时点击右键/中键（无位移），事件滞留缓冲区，**直到用户移动才响应**，表现为点击延迟甚至"丢失"。
- **建议**：只在实际触发的分支内递减，或先确定唯一变化键后一次性 `input_report_key(..., true)`。

### 1.5 Kconfig 缺失驱动代码引用的配置项（功能被静默关闭）【确定问题】

- **位置**：`module/Kconfig`（仅定义 5 个顶层选项）；驱动代码通过 `IS_ENABLED()` / `#define LOG_LEVEL` 引用以下**未定义配置**：

  - `CONFIG_ZMK_INPUT_MOUSE_PS2_ENABLE_ERROR_MITIGATION`（input_mouse_ps2.c:437 误码抑制逻辑**永远关闭**）
  - `CONFIG_ZMK_INPUT_MOUSE_PS2_ENABLE_PS2_RESEND_CALLBACK` / `CONFIG_PS2_GPIO_ENABLE_PS2_RESEND_CALLBACK` / `CONFIG_PS2_UART_ENABLE_PS2_RESEND_CALLBACK`（重发回调关闭）
  - `CONFIG_PS2_GPIO_INTERRUPT_LOG_ENABLED`（中断调试日志永远无法开启）

### 1.7 滚轮符号扩展逻辑错误（scroll 负值解码错误）【确定 Bug，潜伏】

- **位置**：`module/drivers/input_mouse_ps2.c` L510-515（`zmk_mouse_ps2_activity_parse_packet_buffer`）
  ```c
  MOUSE_PS2_SET_BIT(packet.scroll, MOUSE_PS2_GET_BIT(packet_extra, 0), 0);
  MOUSE_PS2_SET_BIT(packet.scroll, MOUSE_PS2_GET_BIT(packet_extra, 1), 1);
  MOUSE_PS2_SET_BIT(packet.scroll, MOUSE_PS2_GET_BIT(packet_extra, 2), 2);
  packet.scroll = packet_extra - ((packet.scroll << 3) & 0x100);
  ```
- **问题**：`packet.scroll`（int8_t）只含 bit0-2（0~7），`(packet.scroll << 3)` 最大 0x38，`& 0x100` **恒为 0**。已做位级模拟验证：负向滚轮 nibble（0x08~0x0F）被解码为 +8~+15（反向猛滚）而非 -8~-1；0x88 → -120。
  - **补充（报告4）**：前三行 `MOUSE_PS2_SET_BIT` 为**无意义死代码**——下一行立即整体覆盖 `packet.scroll`；整个表达式实际等价于 `packet.scroll = (int8_t)packet_extra`（整字节补码截断）。**即使 extra 高 4 位恒为 0，负向滚动依旧解码错误**，并非"碰巧可用"。
- **影响**：当前 DTS 未启用 `scroll-mode`，潜伏；一旦开启即出现滚轮方向/幅度错误。
- **建议**：改为 `packet.scroll = (int8_t)(packet_extra << 4) >> 4;`（4-bit 带符号扩展），或按报告4的写法 `packet.scroll = (packet_extra & 0x0F) - ((packet_extra << 5) & 0x100);` 并删除前三行无意义的 `SET_BIT`。

## 二、P2 中优先级

### 2.1 PS/2 回调单字节缓冲存在丢字节竞争【确定 Bug，低触发概率】

- **位置**：`module/drivers/ps2_gpio.c` L788-799（`ps2_gpio_read_process_received_byte` / `ps2_gpio_read_callback_work_handler`）
- **问题**：`data->callback_byte = byte; k_work_submit_to_queue(...)` 只有一个字节槽。若新字节到达时 worker 尚未执行，前一字节被覆盖丢失。
- **影响**：TrackPoint 3 字节帧中任一字节丢失 → 帧错位 → 触发 resend，形成"丢字节→重发"循环，表现为快速移动时偶发卡顿/跳动。cb 队列优先级较高（2），触发概率低但存在。
- **建议**：改为 FIFO（`K_MSGQ_DEFINE` 32 槽），ISR 侧 `k_msgq_put(K_NO_WAIT)`，worker 侧循环 `k_msgq_get(K_NO_WAIT)` 直至队列空。

### 2.2 PS/2 missed-interrupt 判定后缺少 return【确定逻辑缺陷】

- **位置**：`module/drivers/ps2_gpio.c` L626-633（`ps2_gpio_read_interrupt_handler`）
- **问题**：`prev_cycle_delta_us > PS2_GPIO_TIMING_SCL_CYCLE_MAX` 时调用 `ps2_gpio_read_abort(true, "missed interrupt")` 后**未 return**。abort 已将 `cur_read_pos` 重置为 START、`cur_read_byte` 清零，handler 继续执行会把"已判定超时失效的当前边沿"误当作新帧 start bit 处理。
- **影响**：resend 流程中多一次误解析（随后靠 parity/stop 校验自愈），重同步位置不可靠。
- **建议**：abort 后 `return`。

### 2.3 ps2_gpio.c `dt_flags` 清零复制粘贴错误【确定 Bug】

- **位置**：`module/drivers/ps2_gpio.c` L1317-1319（`ps2_gpio_init_gpio`）
  ```c
  // Overwrite any user-provided flags from the devicetree
  data->scl_gpio.dt_flags = 0;
  data->scl_gpio.dt_flags = 0;   // 应为 data->sda_gpio.dt_flags = 0;
  ```
- **影响**：SDA 保留 DTS 的 `GPIO_PULL_UP`、SCL 丢失——两条线配置不一致（板上有外部 PS/2 上拉时无实际影响，但属明显笔误）。当前 DTS 未给 sda 额外 flags，暂无害。
- **建议**：第二行改为 `data->sda_gpio.dt_flags = 0;`。

### 2.4 LED 引脚三处定义重复 / caps lock 双所有权【确定问题】

- **位置**：`thinkpad_wireless.dts` `leds` 节点（L159-185）；`board.c` L38-44；`status_leds.c` L47-50（魔数宏）
- **问题**：
  1. 同一批 LED 引脚在 DTS、board.c、status_leds.c 三处描述，无单一数据源；
  2. `leds` 节点中除 `caps_lock_led` 被 `zmk,indicator-leds`（DTS L21-27）引用外，其余 5 个 LED 节点（`bt_led`/`bat_led_r/g`/`mute_led`/`mic_mute_led`）**从未被任何行为引用**，实际由 status_leds.c 裸 GPIO 驱动——一旦将来在 keymap 使用 `&bt_led` 等会与裸 GPIO 写冲突；
  3. **caps lock LED 双所有权**：`zmk,indicator-leds` 驱动 P0.31，而 board.c（L85-107 开机流水灯）和 status_leds.c（L104-121 关机流水灯）也直接操作 P0.31，两者会互相覆盖状态。
- **建议**：统一为一个数据源（全部走 DTS `gpio-leds` + 行为，或删除未用节点、集中用宏/枚举定义引脚）；caps lock 二选一（indicator 驱动接管，手动逻辑去掉 P0.31）。

### 2.5 回调队列内 `K_FOREVER` 阻塞【确定隐患】

- **位置**：`module/drivers/input_mouse_ps2.c` L619/624/634/639/649/654（`input_report_key(..., K_FOREVER)`）
- **问题**：该函数运行在 PS/2 callback work queue 线程上下文；移动上报用 `K_NO_WAIT`（L536/539，正确），按键上报却用 `K_FOREVER`——输入队列满时永久阻塞该队列线程。
- **影响**：输入队列异常积压时，PS/2 数据通路被卡死，后续字节丢失。
- **建议**：与移动上报保持一致用 `K_NO_WAIT`，失败时记录/重试。

### 2.6 lint.yml 自动格式化回写 + 无 .clang-format【确定反模式】

- **位置**：`.github/workflows/lint.yml`
- **问题**：`clang-format-15 -i` 直接改写源码后经 `git-auto-commit-action` **自动提交回分支**；仓库根目录**不存在 `.clang-format`**（已确认），将按 clang-format 默认风格随意重排代码并产生无意义 commit；且该 workflow 在 `push` 时无 paths 过滤，任何推送都会触发。
- **建议**：新增 `.clang-format` 固化风格；lint 改为"检查不通过即报错"（`clang-format --dry-run --Werror`），移除自动回写。

- **建议**：删除或加 `IS_ENABLED()` 守卫，避免死代码漂移。

### 2.9 transform 重复矩阵坐标（Studio 幽灵键）【确定问题】

- **位置**：`thinkpad_wireless.dts` `default_transform`（脚本统计 130 条 `RC()` 中 **8 组坐标被重复使用**）：`RC(1,13)×3`（第 5/6/7 行）、`RC(0,13)×2`、`RC(0,14)×2`、`RC(0,15)×2`、`RC(1,14)×2`、`RC(2,13)×2`、`RC(2,14)×2`、`RC(5,15)×2`。
- **影响**：同一矩阵格映射到两个物理位置；当前另一位置是 `&trans` 无实害，但 ZMK Studio 中会出现幽灵键位/重复映射，键位重排后可能产生 ghost。
- **建议**：Unused 行改用唯一坐标或删除；确认 map 长度 = 130（physical layout 键数，当前正确）。

### 2.10 scale-divisor 除零 / 乘法溢出无保护【确定隐患】

- **位置**：`module/drivers/input_listener_ps2.c` L187-188
  ```c
  evt->value = (int16_t)((evt->value * cfg->scale_multiplier) / cfg->scale_divisor);
  ```
- **问题**：`scale-divisor` 配 0 → 除零；`value * multiplier` 用 `int` 运算可能溢出后再截断为 `int16_t`。
- **建议**：加 `scale_divisor == 0` 守卫；中间计算用 `int32_t`。

### 2.11 LED 线程栈偏小【确定隐患】

- **位置**：`module/boards/thinkpad/thinkpad_wireless/status_leds.c` L70 `LED_THREAD_STACK_SIZE 512`
- **问题**：线程内调用 `zmk_usb_is_powered()`、`pwm_set_pulse_dt()`、`gpio_pin_configure()` 等，512 字节偏紧。
- **建议**：至少提升到 1024，并开启栈哨兵（`CONFIG_THREAD_STACK_INFO`/`CONFIG_DEBUG_THREAD_INFO`）实测确认。

### 2.12 CI 产物命名脆弱 + Studio/USB 日志共用 CDC【确定隐患】

- **位置**：`.github/workflows/build.yml`（`create-full-image` job）、`build.yaml`
- **问题**：
  1. `create-full-image` 依赖上游 workflow 产物名 `firmware` 与文件名 `thinkpad_wireless-zmk.hex`，上游命名变化即静默失败；
  2. `build.yaml` 同时启用 `studio-rpc-usb-uart` 与 `zmk-usb-logging`，两者共用同一 CDC ACM 口，日志文本会与 Studio 二进制 RPC 帧交错。
- **建议**：CI 加产物存在性检查；Studio 与日志二选一或分走不同传输。

### 2.13 PWRSWITCH 输入/业务双重管理【设计建议】

- **位置**：`thinkpad_wireless.dts` `direct_kscan`（P1.11）+ `board.c` L53-79 + `status_leds.c` L92-136、L278-279
- **问题**：同一物理输入 P1.11 同时属于 ZMK input subsystem（direct kscan 键位）、board.c 启动阶段轮询、status_leds.c 8 秒关机检测轮询，三处独立管理。
- **建议**：收敛为单一事件源（如 kscan 事件 → 电源管理逻辑），减少竞态与维护面。

### 2.14 board.c 启动路径 busy wait【设计建议】

- **位置**：`module/boards/thinkpad/thinkpad_wireless/board.c` L51-108（`board_gpio_init`，PRE_KERNEL_2）
- **问题**：`GPREGRET == 0xAA`（手动关机后重启）路径中 `k_busy_wait` 累计约 1s（开机灯序）+ 2s（电源键 2 秒确认），在系统初始化阶段阻塞调度。
- **注意**：仅 0xAA 路径触发，正常开机不阻塞。
- **建议**：长按确认改为 GPIO 中断/定时器或 APPLICATION 级线程；若保留，补充注释说明为有意设计。

### 2.15 TrackPoint 参数调节行为因缺少 devicetree 节点完全未编译【确定问题】

- **位置**：`module/Kconfig` L27-29 + `module/CMakeLists.txt` L20 + `module/drivers/behavior_mouse_setting.c`
- **问题**：`CONFIG_ZMK_BEHAVIOR_MOUSE_SETTING` 的 `default y` 条件为 `ZMK_INPUT_MOUSE_PS2 && dt_compat_enabled(zmk,behavior-mouse-setting)`，但**全仓库没有任何 `compatible = "zmk,behavior-mouse-setting"` 的 devicetree 节点**（仅有 binding yaml 与驱动源文件，未实例化）。`dt_compat_enabled` 为假 → 该 Kconfig 默认关闭 → `behavior_mouse_setting.c` **不被编译** → README 声称支持的"灵敏度/负惯性/上限速度/PTS 阈值调节"整套功能完全不可用（不只是没绑定 keymap，是根本没接线）。
- **建议**：在板级 DTS 增加节点实例：
  ```dts
  mouse_setting: mouse_setting {
      compatible = "zmk,behavior-mouse-setting";
      #binding-cells = <1>;
  };
  ```
  并在 keymap 绑定后验证编译产物符号存在。

### 2.16 PWRSWITCH 短按会向主机发送 HID 电源键【确定设计冲突】

- **位置**：`config/thinkpad_wireless.keymap` L24（`&kp C_PWR`）
- **问题**：PWRSWITCH 被绑定为 HID consumer 控件电源键，用户每次短按电源键都会给已连接电脑发送 C_PWR（多数系统默认触发休眠/关机）；而键盘自身的开关机完全由 `board.c`/`status_leds.c` 裸 GPIO 轮询（长按 2s/8s）实现，二者意图冲突。
- **建议**：确认设计意图；若电源键仅用于本机开关机，keymap 改为 `&none`，仅保留固件层长按检测；若确实要透传，需在文档中说明。

### 2.17 Hotkey+PWRSWITCH 实为 &bt BT_CLR，与 README"进入配对"不符【确定文档/行为不一致】

- **位置**：`config/thinkpad_wireless.keymap` L38（`&bt BT_CLR`）；`README.md` L116
- **问题**：README 描述"Hotkey + Power Switch 进入配对广播状态"，实际绑定的是 `BT_CLR`——**清除当前蓝牙配对**（破坏性操作），误触需重新配对。
- **建议**：改用进入配对广播的安全方式（如 `&bt BT_SEL` 后自动广播），或在文档中明确此组合为"清除配对"。

### 2.18 低电量关机未设 GPREGRET 防误触标志【确定设计缺口】

- **位置**：`module/boards/thinkpad/thinkpad_wireless/status_leds.c` L146-166（电池临界关机直接 `sys_poweroff()`）
- **问题**：手动关机路径会写 `NRF_POWER->GPREGRET = MANUAL_POWER_OFF_FLAG`（board.c L29/L51），下次唤醒需"长按 2 秒确认"；低电量关机**未写该标志**，包里误触任意键会完整走"唤醒→发现低电→再关机"循环，每次消耗剩余电量，与防过放初衷相悖。
- **建议**：低电量关机前同样置位 `GPREGRET`（或单独定义低电标志），唤醒后先判电量再决定是否继续启动。

## 四、已核实为正确/无需修改的部分

- **BMD-340 引脚重映射正确**：与 u-blox 官方数据手册（UBX-19033353，Table 2）及网表逐项核对一致——16 个列驱动（DRV0-15）全部落在标准驱动引脚；PS/2 CLK/DATA 在 P0.06/P0.11（标准驱动）；RST P1.01、CHG_INT P1.03 为受限引脚但属静态/低频信号，合规；DTS 内无重复引脚。
- **无 USB 冲突**：nRF52840 的 USB D+/D- 是**独立专用引脚**（QIAA 球 AD6/AD4，模块 pin 67/68），**不是** P0.06/P0.08；网表 USB 正确接 U8.67/68，与 TP4CLK(P0.06)/DRV15(P0.08) 无短路。
- **`GPIO_DS_ALT_*` 移除是必要构建修复**：Zephyr 4.1（ZMK 4.4.1）无此宏（v1.0.34 已确认）；恢复 14mA 高驱动档的正确途径是 Zephyr≥4.2 或在 kscan 初始化后写 `NRF_P0->PIN_CNF[n].DRIVE`。
- **matrix-transform map 长度 130 正确**：ZMK 约束为 map 长度 = physical layout 键数（恰好 130），并非 rows×columns（144）。
- **分区/合并工具自洽**：flash 分区（code 0x26000、storage 0xEC000、boot 0xF4000）、Adafruit bootloader settings 标记（0xFF000，`bank_0=1`）与 `tools/merge_hex.py` 逻辑一致，bootloader hex 与 app hex 无地址重叠（含 UICR 区 0x10001014-0x1000101C）。
- **module.yml 修复到位**：`board_root: module` / `dts_root: module`（此前审查的 P0 已解决）。
- **settings 恢复顺序自洽**：callback 未配置前字节进入 `data_queue`，`settings_load_subtree` 中的 `tp_*_set` 走同步 `ps2_write/read` 同一路径；`is_trackpoint` 在恢复前已检测（有守卫）。无需调整。
